# Location stays in the journal

Connected portal sessions load stays alongside voice recordings in the main journal. `main.tsx` owns a single `useLocationJournal` controller, scoped by both portal owner and session. The controller polls the existing `location_stays` RPC, excludes responses from previous sessions and clears sensitive data on authorization loss. Location failures leave voice recordings available. Sample/demo mode never queries location data. This implementation does not deploy or verify a live backend; repository migration and production readiness must be checked separately.

- `../journal.ts` defines the discriminated `JournalItem` presentation model. Voice entries retain their original `Recording`; stay entries retain their original `Stay`. Stays never become fabricated audio recordings or AI enrichments. Common date, type and search filters, calendar, time strip and map consume the same journal items. A cross-midnight stay appears on each observed date with one original identity for selection/deletion.
- `../JournalStayCard.tsx` uses the existing desktop/mobile card grammar: place candidate, observed time range, fixed observed duration and freshness. Place labels use current settings and do not establish historical associations.
- `StayInspector.tsx` appears in the same detail region and mobile navigation as voice details. It shows observation boundaries, accuracy, map, save-place and explicit permanent deletion. Successful deletion removes the local item before refreshing, so a refresh failure cannot leave a deleted stay visible. Audio, transcription, AI, voice exports and audio trash remain voice-specific.
- `LocationLauncher.tsx` opens **Place settings**, not a parallel stay browser. `LocationWorkspace.tsx` handles optional synchronization consent, saved places, recommendations and cloud data management through the shared controller. Enabling on the web does not start watch collection or silently activate a watch that has never opted in. Previous-stay backfill defaults off.
- `types.ts` follows `docs/architecture/location-stays-sync.md` wire stay fields. `domain.ts` provides observation freshness, calendar/DST slices, conservative recording association candidates, place validation and overlap detection.
- `PlaceEditor.tsx` and `PlaceMap.tsx` provide place creation/editing. The map center is set by tapping the map or by dragging its handle; the drag edits the draft only, so overlap acknowledgement, `expectedRevision` conflicts and Save still gate the write. Numeric coordinate fields remain the keyboard path. `expectedRevision` is the server's **place collection revision**, not the individual place revision. Transient refresh failures retain the draft; authorization loss clears it. Conflicts preserve the draft until the user loads and reviews the latest value and explicitly reapplies it. Overlap acknowledgement does not assign past recordings to that place.
- `recommendations.ts` uses provisional conservative 100m clustering, accuracy <=30m and 30-minute fragment suppression. It never fills observation gaps. `dismissals.ts` stores owner-scoped preferences for at most seven days, ending no later than their source stays' earliest expiry. Stay deletion, observed revocation and sign-out clear these preferences.

Run pure tests and the production build with:

```sh
npm test --prefix web
npm run build --prefix web
```

`web/e2e/unified-journal.spec.ts` covers mixed ordering, shared filters/search, observed duration, type-specific details/deletion, authorization loss, backend unavailability, midnight dates and mobile navigation/themes. `web/e2e/stays-followup.spec.ts` covers place editing recovery/conflicts and hidden-coordinate cleanup. These use mocked RPCs, not live backend evidence. Real device/backend synchronization and broader accessibility evidence remain release checks. Watch-side consent reconciliation adopts a web re-enable's bumped token and disables locally on server revocation (`LocationSyncClient.ensureConsentCurrent`). See the [follow-up checklist](../../../docs/design/location-stays-followup.md).

The existing location backend is deployed as recorded in [Deployment status](../../../docs/architecture/location-stays-sync.md#deployment-status). The [2026-10-26 portal pass](../../../docs/validation/2026-10-26-portal-pass/README.md) records live measurements of the earlier standalone workspace, not acceptance of this redesigned journal.
